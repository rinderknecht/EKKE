\begin{frame}
  \frametitle{Garbage Collection}

  The runtime systems of many programming languages feature
  \textbf{dynamic memory management}.

  \bigskip

  The first aspect of that management is \textbf{allocation}, that is,
  the execution of the program can create pieces of data (called
  \textbf{objects} in this context) that can outlive the function that
  created them, even last the total running time.

  \bigskip

  Those objects exist in a memory area called the \textbf{heap}. More
  precisely, a \textbf{continuous block} is allocated for each object,
  whose size depends on the \textbf{type} of the object.

\end{frame}

\begin{frame}[containsverbatim]
  \frametitle{Garbage Collection}

  For example, in \Java, we can declare a type for the cells
  in a linked list of integers as follows:
\begin{verbatim}
class Cell {
  int   content;
  Cell  next;
}
\end{verbatim}
Each cell contains an integer and a \textbf{pointer} to another
cell. The pointer is implicit in the recursive occurrence of the type
name \texttt{Cell}. Here, the field \texttt{content} is a primitive
type, so it is not a pointer.

\bigskip

A pointer is either the address of an object in memory, or a special
value \textbf{nil} (noted \texttt{null} in \Java). Consequently, each
cell requires at least two \textbf{words} (one for each field and
perhaps more, depending on the data layout).

\end{frame}

\begin{frame}[containsverbatim]
  \frametitle{Garbage Collection}

  A cell can be allocated with the built-in function `\texttt{new}',
  like so:
\begin{verbatim}
Cell c = new Cell ();
\end{verbatim}

A word is the smallest amount of memory that can be
addressed and filled by a primitive type or a pointer ---~64
bits in modern computers.

\bigskip

In other words, we can imagine memory as an array of words indexed by
addresses. Those words may be interpreted as an address or a primitive
type.

\bigskip

Then we can modify the contents of the fields, as many times as we
wish to. Every call to `\texttt{new}' returns the \textbf{address of a
  new block} drawn from the available memory.

\end{frame}

\begin{frame}[containsverbatim]
  \frametitle{Garbage Collection}

Because each allocation removes from available, finite memory, it is
necessary for the GC to \textbf{free the memory used by useless
  objects}, which it needs to define and find.

\bigskip

In some programming languages, like \C, this task is entirely
delegated to the programmers. They have a predefined procedure
`\texttt{free}' that frees a memory block:
\begin{verbatim}
free(c);
\end{verbatim}
After it is executed, the block pointed at by~`\texttt{c}' is
considered available again, so its address can be reused by a future
allocation.

\end{frame}


\begin{frame}[containsverbatim]
  \frametitle{Garbage Collection/Memory leak}

  \label{C_errors}

  In \C, the premature release of an object may lead to errors:
  \begin{center}
    \includegraphics[width=0.8\textwidth]{wrong_free.png}
  \end{center}
  Here, \texttt{B} has been freed. The live object \texttt{A} now
  contains a \textbf{dangling pointer}, and the memory occupied by
  \texttt{C} has \textbf{leaked}: \texttt{C} is not reachable, but it
  cannot be freed.

  \bigskip

  Another common mistake is freeing an already freed object (like
  \texttt{B} above): this is an undefined behaviour in \C, and thus a
  source of \textbf{non\hyp{}determinism}.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  In \Java, there is no equivalent to the `\texttt{free}' procedure of
  \C because the identifying and freeing of useless objects is left to
  the runtime system.

  \bigskip

  That part of the runtime is called the \textbf{garbage collector}
  (GC), or `collector' in short. At regular intervals, it interrupts
  the program (called hereafter the \textbf{mutator}), analyses the
  heap, find out some or all useless objects, and frees them.

  \bigskip

  This technique was invented by McCarthy, creator of the functional
  programming language \Lisp in \oldstylenums{1960}. It is widely used
  in mainstream languages like \Java, \Csharp, \Haskell or \OCaml.

  \bigskip

  Beyond avoiding the two errors above, a GC may also free many
  objects at a time, which is more efficient than any sequential,
  manual deallocation.

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection}

  How does a GC determine what objects are useless, since it has no
  access to the source code or the programmer (interactively)?

  \bigskip

  The GC can rely on the following condition:
  \begin{center}
    \it If, at a certain moment, a program does not have (anymore) a
    pointer to an object, that object is considered useless.
  \end{center}
  That condition is not true in \C, where pointers can be forged from
  integers (by type casting), but it holds in \Java for example.

  \bigskip

  Therefore, the memory block of that object can be reused for
  another, without the program being able to observe that reuse.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Roots \& Liveness}

  When, at the current point in the execution of a program, the
  address of an object is known, that object is said to be
  \textbf{alive}, and \textbf{dead} otherwise.

  \bigskip

  We can define inductively the notion of liveness:
  \begin{definition}
    \it Both the global and local variables of the program are called
    \textbf{roots}. By definition (base case), the object pointed at
    by a root is alive. Moreover, if an object is alive and one of its
    fields contains the address of another object, then that object is
    alive too (inductive case).
  \end{definition}

  \medskip

  What counts as global and local variable depends on the programming
  language. In \Java, the former are the `\texttt{static}' fields
  (a.k.a. instance fields), and the latter are methods arguments
  (including `\texttt{this}') and the variables declared in the method
  being executed.

  \end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  The heap can now be seen as a \textbf{graph}, where the
  \textbf{vertices} correspond to the roots and the objects, and the
  \textbf{edges} model the pointers between objects (that is, if one's
  block contains a pointer to another's).

  \bigskip

  Sometimes we will use interchangeably `block' and `object' when
  referring to blocks in the heap. Likewise `pointer' and `address'.

  \bigskip

  The live objects are then the vertices \textbf{reachable from the
    roots}.

  \bigskip

  Therefore, to determine the live objects at a given time, the GC has
  to traverse the graph of objects from the roots.

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection}

  We started this introduction by referring to `useful objects', but
  now we see that the appropriate concept is that of `live objects',
  which is the same as `reachable objects'.

  \bigskip

  It is obvious that all dead objects are useless, but the reciprocal
  is not true: a live object might be useless if the program does
  nothing with it. They are allocated in the heap but cannot be
  reclaimed. This is a case of \textbf{memory leak}. (We saw
  page~\pageref{C_errors} another case of memory leak in \C.)

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Mark \& Sweep}

  One of the simplest technique for garbage collection is known as
  \textbf{mark \& sweep}.

  \bigskip

  As the name indicates, it consists of two passes:
  \begin{enumerate}

    \item mark: traversing the \emph{graph} of objects from the roots
      while marking the visited nodes,

    \item sweep: traverse the \emph{whole} heap (the linear piece of
      memory, not the graph view): all the unmarked objects are freed,
      and the marks of the others are reset (to mean `not visited').

  \end{enumerate}
  Crucially, during the mark \& sweep, \textbf{the mutator is
    stopped}.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Marking}

  In the following pseudo\hyp{}code, we will assume that each
  object~\(o\) has two fields, \(o.\text{left}\) and
  \(o.\text{right}\), each containing a pointer to another object, or
  the special value \texttt{nil}. Each object also contains a
  \textbf{bit field} denoting the states `marked' and `unmarked'
  (default): this is part of the \textbf{metadata}.

  \bigskip

  Obviously, the bit marks from the first phase constitute the
  information carried over to the sweeping phase, but they also play
  an essential rôle during marking: they tell the traversal algorithm
  to not visit a vertex more than once, so the total cost of
  traversing the graph remains \textbf{linear in the number of
    vertices}.

  \bigskip

  This is crucial if some objects are shared through distinct paths,
  in particular if the graph contains cycles.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  We stated earlier that each object would contain a bit field for the
  mark. This is the most common solution: put the mark into a
  \textbf{header}, that is, metadata about each object. The downside
  is that the cost per object becomes (at least) one word, even if
  only a bit is required and there is only one field of data (that is
  the worst case: the size of the metadata is the same as that of the
  data).

  \bigskip

  There is another choice: a separate table, called a \textbf{bitmap},
  where the bits are stored in a compact manner: one word will encode
  many bit marks (64 on modern hardware architectures). This enables
  getting rid of the object headers and saving a lot of memory,
  especially if there are many small objects, at the expense of extra
  time accessing and decoding the table (mapping object addresses to
  bit positions and vice\hyp{}versa).

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Recursive Marking}

  For the marking of objects, any graph traversal can do. For example,
  let us run a \textbf{depth\hyp{}first search} from each root:

  \bigskip

  \begin{codebox}
    \(\proc{DFS}(o)\)\\
    \li \If \(o \neq \kw{nil}\) \kw{and} \(o\) is not marked
    \li \Then \text{mark} \(o\)
    \li       \proc{DFS}(o.left)
    \li       \proc{DFS}(o.right)
        \End
  \end{codebox}
  Note how we use indentation to suggest blocks of
  instructions. Finally:
  \begin{codebox}
    \(\proc{Mark}()\)\\
    \li \For \kw{each} root \(r\) \kw{do} \proc{DFS}(r)
  \end{codebox}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  This program terminates because the bit marks are never set twice
  nor reset.

  \bigskip

  Let us count the number of calls to \proc{DFS}, including the
  recursive calls. First, there is one call for each root. Second, two
  recursive calls per object being marked. Therefore, the total number
  of calls to \proc{DFS} is \(O(r + m)\), where \(r\)~is the number of
  roots, and \(m\)~is the number of marked objects.

  \bigskip

  Moreover, the flipping of the bit mark is assumed to take a constant
  time: \(O(1)\).

  \bigskip

  Note that \(m\)~only counts the live objects: if there are many dead
  objects, the cost does not change here.

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection/Iterative Marking}

  The previous pseudo\hyp{}code uses function calls, but it is better
  for the collector to not modify the call stack, which is meant for
  the mutator.

  \bigskip

  Let us write a single loop instead, one that manages a stack of
  pointers to be traversed.
  \begin{codebox}
    \(\proc{Mark}()\)\RComment Iterative definition \\
    \li \For \kw{each} root \(r\) \kw{do} push \(r\);
    \li \While the stack is not empty \kw{do}
    \li \> pop a pointer \(o\)
    \li \>  \If \(o \neq \kw{nil}\) \kw{and} \(o\) is unmarked
    \li     \Then mark \(o\)
    \li           push \(o\).left
    \li          push \(o\).right
            \End
  \end{codebox}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  We could have used a data structure other than a stack, because the
  order in which the objects are visited does not matter.

  \bigskip

  We also could avoid pushing \textbf{nil} pointers.

  \bigskip

  If we interpret \(o\)~as a linked list so that \(o\).left points to
  the contents of the cell, and \(o\).right points to the next cell,
  then what is the behaviour of the code above? In particular, what is
  the size of the stack?

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection}

  We see that \(o\).left is pushed \emph{before} \(o\).right, so the
  next pointer to be popped is \(o\).right, and so forth until the end
  of the list, that is \(o\).right is \textbf{nil}. So the size of the
  stack ends up being the same as the list's. If the list is large,
  this might be a problem.

  \bigskip

  Instead, we could \textbf{push} \(o\).left \textbf{after}
  \(o\).right. This way, the contents of a cell would be traversed
  before the next cell, that is, the rest of the list. Therefore the
  traversal cost (in terms of memory) does not depend on the size of
  the list.

  \bigskip

  In a functional programming language, lists are the bread and butter
  of programmers, therefore a GC traversing the head before the tail
  of the list is a significant improvement.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Efficient Marking}

  \begin{codebox}
    \(\proc{Mark}()\)\RComment Second redefinition, more efficient \\
    \li \For \kw{each} root \(r\) \kw{do} push \(r\)
    \li \While the stack is not empty \kw{do}
    \li \> pop a pointer \(o\)
    \li \> \If \(o \neq \kw{nil}\) \kw{and} \(o\) is unmarked
    \li    \Then mark \(o\)
    \li          push \(o\).right\RComment Right first
    \li          push \(o\).left
           \End
  \end{codebox}
\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Traversal Stack}

  \label{Mark}

  In general, an object will have more than two pointers, and the
  previous optimisation applies only because the compiler somehow
  informed the GC that this is a value of the list data type.
  \begin{codebox}
    \(\proc{Mark}()\)\RComment General depth-first traversal\\
    \li \For \kw{each} root \(r\) \kw{do} push \(r\)
    \li \While the stack is not empty \kw{do}
    \li \> pop a pointer \(o\)
    \li \> \If \(o \neq \kw{nil}\) \kw{and} \(o\) is unmarked

    \li          \For \kw{each} \(c\) \kw{in} \(\proc{Children}(o)\) \kw{do}

    \End

\begin{frame}
  \frametitle{Garbage Collection}

  But how \proc{Children} knows what fields of an object are pointers
  and which are not, for example, integers and floating\hyp{}point
  numbers? There are several approaches.
  \begin{itemize}

    \item Like a bitmap can be used to keep track of allocated
      objects, the header of an object can contain a bitmap for the
      fields that are pointers.

    \item The first bit of words can be used to distinguish pointers
      and scalars. For example, \OCaml uses only 63 bits to encode
      values, including pointers, as the leftmost bit is used to
      `type' them.

    \item If words have a valid interpretation as pointers, we can
      assume they are pointers. This what \textbf{conservative GCs}
      do. They over\hyp{}approximate live objects, so some dead
      objects might not be freed. This what GCs for \C and \Cpp do
      (those languages have no GC by default).

  \end{itemize}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Traversal Stack}

  As we saw in the program page~\pageref{Mark}, the size of the
  traversal stack can be linear in the size of the reachable data. But
  how is that stack implemented?

  \bigskip

  It cannot be allocated in the heap with the mutator's data, as the
  heap must remain the same during a collection. Instead, it relies on
  an array whose size is fixed beforehand (static data for the
  collector).

  \bigskip

  An element of that array then fits in a word (interpreted as an
  address), which is optimal.

  \bigskip

  Nevertheless, if the heap can contain up to \(n\)~objects, that
  array should be of size~\(n\), even if not used
  completely. Moreover, if each block contains at least three words (a
  header and two pointers), then the length of the stack-array should
  be a third of that of the heap, which is considerable.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  One obvious solution is having \textbf{a bounded stack} that is not
  too large.

  \bigskip

  If it becomes full, we drop any new pointer. At the end of the
  marking, the collector would know that the graph was not traversed
  entirely (because a stack overflow sets a flag, for instance).

  \bigskip

  In that case, a linear sweep of the whole heap is performed:
  whenever a marked object is found to point to an unmarked object, we
  run the marking algorithm from it, as if it were a root. This
  process is iterated until a fixed point (no new object is marked):
  all reachable objects have then been marked.

  \bigskip

  Additionally, in case of a stack overflow, the size of the stack can
  be doubled for the next collection.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Pointer Reversal}

  Another solution by Deutsch, Schorr and Waite (DSW), more complex,
  consists in dispensing with the stack entirely. Instead, the
  pointers in the heap are modified to keep track of the path of the
  marking.

  \bigskip

  Let us illustrate the basic technique behind DSW, called
  \textbf{pointer reversal}, on a singly\hyp{}linked list containing
  only primitive types, so each object~\(o\) has exactly one
  pointer~\(o\).next. For instance
  \[
  A \longrightarrow B \longrightarrow C \longrightarrow \textbf{nil}
  \]
  The collector starts the traversal from~\(A\) without a stack

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  Initially:
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \hphantom{\longleftarrow} & A & \longrightarrow & B &
    \longrightarrow & C & \longrightarrow & \textbf{nil} \\
    \uparrow   && \uparrow && \uparrow \\
    p          && q        && r
  \end{array}
  \]

  \medskip

  The DSW maintains three pointers:
  \begin{enumerate}

    \item \(q\)~points to the current node being visited (to be
      marked or already marked);

    \item \(p\)~points to the previous visited node (e.g. \(p
      \rightarrow \textbf{nil}\) if \(q \rightarrow A\));

    \item \(r\)~points to the rest of the list (e.g. \(r \rightarrow
      \textbf{nil}\) if \(q \rightarrow C\)).

  \end{enumerate}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection} We can mark~\(A\) (becomes \(A^*\))
  and set \(A\).next to point backwards to~\(p\):
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \hphantom{\longrightarrow} & B
    & \longrightarrow & C & \longrightarrow & \textbf{nil} \\
    \uparrow   && \uparrow && \uparrow          \\
    p          && q        && r
  \end{array}
  \]
  Then we move \(p\), \(q\)~and~\(r\) one step to the right:
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \hphantom{\longrightarrow} & B
    & \longrightarrow & C & \longrightarrow & \textbf{nil} \\
    && \uparrow && \uparrow && \uparrow \\
    && p        && q        && r
  \end{array}
  \]

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection}

  We can mark~\(B\) and set \(B\).next to point backwards to~\(A^*\):
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \longleftarrow & B^*
    & \hphantom{\longrightarrow} & C & \longrightarrow & \textbf{nil} \\
    && \uparrow && \uparrow && \uparrow \\
    && p        && q        && r
  \end{array}
  \]
  Then we move \(p\), \(q\)~and~\(r\) one step to the right:
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \longleftarrow & B^*
    & \hphantom{\longrightarrow} & C & \longrightarrow & \textbf{nil} \\
    &&&& \uparrow && \uparrow && \uparrow \\
    &&&& p        && q        && r
  \end{array}
  \]

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  We can mark~\(C\) and set \(C\).next to point backwards to~\(B^*\):
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \longleftarrow & B^*
    & \longleftarrow & C^* & \hphantom{\longrightarrow} & \textbf{nil} \\
    &&&& \uparrow && \uparrow && \uparrow \\
    &&&& p        && q        && r
  \end{array}
  \]
  We are done. To return, we need to reverse the pointers again using
  the same algorithm, except this time we start swapping
  \(p\)~and~\(r\):
  \[
  \begin{array}{ccccccccc}
    \textbf{nil} & \longleftarrow & A^* & \longleftarrow & B^*
    & \longleftarrow & C^* & \hphantom{\longrightarrow} & \textbf{nil} \\
    &&&& \uparrow && \uparrow && \uparrow \\
    &&&& r        && q        && p
  \end{array}
  \]
  The general case (trees, graphs) is more complicated, but this gives
  the gist of it.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Sweeping}

  Let us consider now the second phase: sweeping.

  \bigskip

  During marking, we considered the graph of objects. Now we look at
  the heap as an array of words indexed by addresses. (This dual view
  of the heap, either as a graph or an array, is crucial in
  understanding garbage collection.)

  \bigskip

  In such a view of the heap, we see a series of blocks, either
  allocated to objects or free --- both kinds starting with a header.

  \bigskip

  To understand how to sweep unreachable objects, we first need to
  know how objects were allocated first.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Allocation with Free Lists}

  Let us assume that the collector
  \begin{itemize}

    \item can distinguish allocated blocks from those that are free to
      use;

    \item can determine the size of each block (allocated and free);

    \item maintains the set of all free blocks in a \textbf{free
      list}.

  \end{itemize}
  Objects have a header. \textbf{Free blocks need a header} too:
  \begin{enumerate}

    \item to distinguish an allocated object from a free block, we
      store in the first word a \textbf{number unique to all free
        blocks};

    \item in the second word, the \textbf{size of the block}.

    \item Since free and allocated blocks share the same space (no
      partitioning of the heap), we need to connect all the free
      blocks in a manner reminiscent of how the objects are
      interconnected in a graph. So the third word of their header
      contains a \textbf{pointer to the next free block}, making up
      the free list. The address of the first free block will be held
      in a global variable.

  \end{enumerate}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  In all, free blocks require three-word headers, which is acceptable,
  as, for instance, we have seen that a simple linked list requires
  three words of data (plus the header, which is metadata).

  \bigskip

  The free list will require three main operations:
  \begin{enumerate}

    \item a predicate \(\proc{IsEmpty}()\) on whether the free list is
      empty;

    \item a procedure \(\proc{Allocate}(o)\) that looks up a free
      block large enough to contain the object~\(o\), allocates and
      initialises the memory, and updates the free list (leaving
      perhaps a smaller free block behind), and otherwise fails;

    \item a procedure \(\proc{Free}(a)\) that turns the object
      allocated at address~\(a\) into a free block that is in turn
      registered with the free list, perhaps after coalescing it with
      any contiguous ones.

  \end{enumerate}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Sweeping}

  Assuming a free list and the previous primitive operations, we can
  return to the second phase of the collector: sweeping.
  \begin{codebox}
    \(\proc{Sweep}()\)\\
    \li \(a \gets \text{start of the heap}\)\RComment There is always a
    block at address \(a\)
    \li \While \(a < \text{end of the heap}\) \kw{do}\RComment
    Increasing addresses
    \li \> \(n \gets \proc{Size}(a)\)\RComment Includes the header
    \li \> \If \(a\) is an allocated object \(o\)\RComment All blocks
    have a header
    \li    \Then \If \(o\) is marked\RComment \(o\) is alive
    \li          \Then remove the mark\RComment Write the header
    \li          \Else \proc{Free}(a)\RComment \(o\) is dead
                 \End
           \End
    \li \> \(a \gets a + n\)
  \end{codebox}
  Note how we call \(\proc{Size}(a)\) \emph{before} calling
  \(\proc{Free}(a)\), as the latter could destroy the information
  needed by \proc{Size}, by coalescing the newly freed block with
  another.

\end{frame}

\begin{frame}
  \frametitle{Garbage Collection/Allocation}

  We can now write the GC procedure \proc{New} that is called by the
  runtime system:
  \begin{codebox}
    \(\proc{New}(o)\)\\
    \li \If \(\proc{IsEmpty}()\)\RComment Checking the free list
    \li \Then \(\proc{Mark}()\)\RComment Marking live objects
    \li       \(\proc{Sweep}()\)\RComment Reclaiming dead objects
    \li       \If \(\proc{IsEmpty}()\)\RComment Checking again
    \li       \Then \(\proc{New} \gets \kw{nil}\)\RComment Memory is
    really full
    \li       \Else \(\proc{New} \gets \proc{Allocate}(o)\)\RComment See next line
              \End
    \li  \Else \(\proc{New} \gets \proc{Allocate}(o)\)\RComment Fails if \(o\)
    doesn't fit
         \End
  \end{codebox}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/First-fit Allocation}

  Several implementations of \proc{Allocate} are possible. Perhaps the
  simplest is \textbf{first-fit allocation}, whereby the first block
  in the free list that can fit the object is used.

  \bigskip

  Let \(\proc{Next}(p)\) be the address of the free block immediately
  after the free block~\(p\). It is an \(l\)\hyp{}value, and
  \(\proc{Size}(p)\) too. The value \(\proc{Size}(o)\) is the size
  of~\(o\) as recorded in its header. Let \textbf{free} be the head of
  the free list.
  \begin{codebox}
    \(\proc{FirstFit}(o)\)\RComment Use in stead of \proc{Allocate} in
    \proc{New}\\
    \li \((\id{previous}, \id{current}) \gets (\kw{nil}, \kw{free})\)
    \li \While \(\id{current} \neq \kw{nil}
               \,\; \kw{and} \,\; \proc{Size}(current) <
               \proc{Size}(o)\) \kw{do}
    \li \> \((\id{previous}, \id{current})
    \gets (\id{current}, \proc{Next}(\id{current}))\)
    \End
    \li \kw{if} \(\id{current} \neq \kw{nil}\) \kw{then} \(\proc{Update}(\id{previous},
    \id{current}, o)\)
    \li \(\proc{FirstFit} \gets \id{current}\)
  \end{codebox}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  Let us use the beginning of a free block to allocate an object:
  \begin{codebox}
    \(\proc{Update}(\id{previous}, \id{current}, o)\)\RComment
    \(\proc{Size}(current) \geqslant \proc{Size}(o)\)\\
    \li \If \(\proc{Size}(current) = \proc{Size}(o)\)
    \li \Then \(\proc{Next}(previous) \gets
    \proc{Next}(current)\)\RComment Drop the block
    \li \Else \(\id{rest} \gets \id{current} + \;
    \proc{Size}(o)\)\RComment Header size managed
    \li       \(\proc{Next}(rest) \gets \proc{Next}(current)\)
    \li       \(\proc{Size}(rest) \gets \proc{Size}(current) - \proc{Size}(o)\)
    \li       \(\proc{Next}(previous) \gets \id{rest}\)
        \End
    \li \(\proc{Write}(\id{current}, o)\)
  \end{codebox}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/First-fit Allocation (variant)}

  We could instead use the end of the free block:
  \begin{codebox}
    \(\proc{Update}(\id{previous}, \id{current}, o)\)\RComment
    \(\proc{Size}(current) \geqslant \proc{Size}(o)\)\\
    \li \If \(\proc{Size}(current) = \proc{Size}(o)\)
    \li \Then \(\proc{Next}(previous) \gets \proc{Next}(current)\)
    \li       \(\proc{Update} \gets \id{current}\)
    \li \Else \(\proc{Size}(current) \gets \proc{Size}(current) - \proc{Size}(o)\)
    \li       \(\proc{Update} \gets \id{current} + \; \proc{Size}(current)\)
        \End
    \li \(\proc{Write}(\proc{Update}, o)\)
  \end{codebox}
  Note how \proc{Update} must be a function: it returns the address of
  the allocated block, and so \proc{FirstFit} should be rewritten
  slightly.

  \bigskip

  How to fuse the remaining free block, if any, with a contiguous one
  (lower or higher, depending where the object is allocated)? This is
  called \textbf{coalescence}, which reduces fragmentation.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Next-fit Allocation}

  First-fit allocation tends to accummulate small free blocks at the
  beginning of the free list, slowing further allocations.

  \bigskip

  To avoid this, \textbf{next-fit allocation} starts searching a free
  block where the last allocation succeeded. When the end is reached,
  search resumes at the beginning, hence it is sometimes called
  \emph{circular next-fit allocation}.

  \bigskip

  One drawback is that objects from different phases of the mutator
  execution become mixed together, and, because they die at different
  times, this increases fragmentation.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Best-fit Allocation}

  \textbf{Best-fit allocation} finds the first smallest free block
  that fits the object, thus not splitting large blocks that would
  otherwise fit future, larger objects.
  \vspace*{-5mm}
  \begin{codebox}
    \(\proc{BestFit}(o)\)\\
    \li \((\id{bestPrev}, \id{best}, \id{bestSize}, \id{previous}, \id{current})
          \gets (\kw{nil}, \kw{nil}, \infty, \kw{nil}, \kw{free})\)
    \li \While \(\id{current} \neq \kw{nil}\) \kw{do}
    \li \> \If \(\proc{Size}(o) \leqslant \proc{Size}(\id{current})
                < \id{bestSize}\)
    \li    \Then \((\id{bestPrev}, \id{best}, \id{bestSize}) \gets
                   (\id{previous}, \id{current}, \proc{Size}(current))\)
           \End
    \li \> \((\id{previous}, \id{current}) \gets (\id{current}, \proc{Next}(current))\)
    \li \If \(\id{best} = \kw{nil}\)
    \li \Then \(\proc{BestFit} \gets \kw{nil}\)
    \li \Else \(\proc{BestFit} \gets \proc{Update}(bestPrev, best, o)\)
        \End
  \end{codebox}
  The loop always traverses the free list entirely, whereas
  \proc{FirstFit} could stop at the head of the list.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Drawbacks of Free Lists}

   When allocating objects of different sizes, the heap will contain
   holes (free blocks) of varying sizes: this is
   \textbf{fragmentation}.
   \begin{enumerate}

     \item This may lead to an \textbf{allocation failure} because an
       object can fit in none of those, even if the total available
       memory is large enough.

     \item Another unpleasant effect of fragmentation is when two
       successive allocation requests are satisfied by free blocks
       that are very far apart in the free list: this breaks data
       locality, which incurs \textbf{cache misses} and virtual page
       loads.

     \item Yet another drawback of a free list is simply its linear
       structure, yielding an allocation to be performed in
       \textbf{linear time} in the worst case.

   \end{enumerate}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Improving Free Lists}

  In a first\hyp{}fit context, a special case of Cartesian trees
  called \emph{treaps} are useful to speed up search, as they are
  totally ordered by addresses (like a BST) and partially by sizes
  (like a heap).

  \bigskip

  In a best\hyp{}fit allocation strategy, the whole free list is
  always traversed.

  \bigskip

  We could speed up the search by having the free blocks in a
  \textbf{balanced search tree} ordered by sizes (as keys), for
  example an AVL tree or a red\hyp{}black tree (RBT). This yields an
  \(O(\log n)\) \emph{worst case} cost, where \(n\)~is the number of
  available blocks.

  \bigskip

  In passing, it is then better to call this structure a \textbf{free
    pool}.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Improving Free Lists}

  The height invariant of AVL trees is tricky to get right, and
  deletion in RBTs is also difficult.

  \bigskip

  For simpler implementations, but only with a logarithmic
  \emph{average cost}, \textbf{binary search trees} (BSTs) are a good
  compromise, or splay trees.

  \bigskip

  By far, the binary search trees are the simplest to implement.

  \bigskip

  It then saves time to enter only blocks of each size in the BST, and
  to chain from that node the other blocks of same size: this speeds
  up search, but also yields less rotations after a deletion.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Sequential Allocation}

  A completely different way to address the locality and linearity
  issues is \textbf{sequential allocation} whereby \textbf{the heap is
    partitioned in two} areas: one for the objects (dead or alive) and
  a \textbf{free zone adjacent to it}. The GC has a pointer to the
  start of the free zone, and another to the upper limit of that zone
  (to avoid overwriting in case of overflow). A new object of
  size~\(n\) is allocated at that address (modulo some alignment

\begin{frame}[containsverbatim]
  \frametitle{Garbage Collection/Pointer Alignement}

  To illustrate pointer alignement, consider a word size of~4 bytes in
  \C:
\begin{verbatim}
struct Example {
    char  a;   // 1 byte
    int   b;   // 4 bytes = 1 word
    char  c;   // 1 byte
};
\end{verbatim}
A value of this type does \textbf{not} occupy 6~bytes, but~12:
\begin{itemize}

  \item `\texttt{a}' starts at offset~0 (1~byte used);

  \item 3~bytes of padding are inserted so `\texttt{b}' starts at
    offset~4 (the closest multiple of~4);

  \item `\texttt{b}' starts at offset~4 (4 bytes uses);

  \item `\texttt{c}' starts at offset~8 (1 byte used);

  \item 3~bytes of padding are added at the end so the whole structure
    is a multiple of 4~bytes (word size), which is needed for uniform
    indexing of arrays of values of type `\texttt{Example}'.

\end{itemize}

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Sequential Allocation}

  We assume that the collector
  \begin{itemize}

    \item can determine the size of a block by means of \proc{Size},

    \item and manages a pointer \textbf{free} to the start of the free
      zone, and another, \textbf{limit}, to the upper limit of that
      zone.

  \end{itemize}
  \begin{codebox}
    \(\proc{SeqAlloc}(o)\)\RComment \(o\) is an object\\
    \li \(\id{free'} \gets \kw{free} + \proc{Size}(o)\)\RComment Read
    the header of \(o\)
    \li \If \(\id{free'} > \kw{limit}\)
    \li \Then \(\proc{SeqAlloc} \gets \kw{nil}\)\RComment Insufficient memory
    \li \Else \(\proc{Write}(o, \kw{free})\)\RComment At the address \kw{free}
    \li       \(\kw{free} \gets \id{free'}\)\RComment Bump pointer
    \li       \(\proc{SeqAlloc} \gets \kw{free}\)
        \End
  \end{codebox}
  No linear search. Locality enables good cache performance. But, if
  objects are never moved, deallocations will create free blocks that
  cannot be reused, simply because they are not in the free zone: we
  still have the core problem of \textbf{fragmentation}.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection/Copying collectors}

  There is a class of collectors that \textbf{move/copy objects} after
  they have been allocated, in particular to move them next to each
  other. This is called \textbf{compaction}, and it gets rid of
  fragmentation until the next cycle.

  \bigskip

  The simplest of copying collectors is Cheney's algorithm.

  \bigskip

  The general idea is simple enough. The heap is divided in two spaces
  of same size: one where allocation occurs, one free. Whenever the
  former is full, the live objects are scanned and copied next to each
  other at the start of the latter. Then the rôle of the two
  semispaces is reversed, in particular, dead objects are not
  collected individually: the whole semispace where they are is now
  \emph{considered} free.

  \bigskip

  Care must be taken to preserve sharing when copying the objects.

\end{frame}

  The original semispace is named \textbf{from-space} to distinguish

  created from the latter.

  \bigskip

  There is a \textbf{scan pointer} in the call stack that scans
  (downwardly) the words in the current frame, skipping scalars. We
  copy the block pointed by the first pointer, and bump the
  \textbf{allocation pointer} in the to-space.

  \bigskip

  The pointer in the stack is then updated with the copy. (Previous
  value with a dashed line.)

  \bigskip

  The original block header is overwritten with a pointer to the copy:
  this is the \textbf{forwarding pointer} (in grey). Forwarding
  pointers are used to preserve sharing during copying.

  \bigskip

  The last pointer of the frame goes to the already copied block, and
  is updated with the forwarding pointer.

  \bigskip

  We already can see that Cheney's algorithm performs a

  tale being the space between the scan pointer and the allocation
  pointer being used as a queue of objects to traverse. (These are
  sometimes called \textbf{grey}, whereas \textbf{white} objects are
  those alive and \textbf{black} objects are dead).

  \bigskip

  Breadth\hyp{}first breaks some locality, as parents, children and
  grand\hyp{}children objects find themselves compacted far away from
  each other if they have lots of siblings.

\begin{frame}
  \frametitle{Garbage Collection/Generational collector}

  It was observed that new objects die young. Moreover, in functional
  languages, those objects tend to be small (about three words of
  contents).

  \bigskip

  Therefore we'd like to scan new blocks more frequently, and scan
  older blocks more rarely. This distinction, young versus old
  objects, each allocated in two separate spaces of the heap, gives
  rise to \textbf{generational collectors}.

  \bigskip

  Each space, called a generation, can use their own collecting
  algorithm, as long as, after the collection of the young generation,
  the live young objects are promoted into the old generation.

  \bigskip

  Cheney's algorithm is a good choice for the young generation,
  because its cost is proportional to the number of live objects: if a
  lot of objects die young, the generation can be small and compaction
  cost remain low.

\end{frame}


\begin{frame}
  \frametitle{Garbage Collection}

  There are a lot more GC algorithms that we cannot cover, like
  \begin{itemize}

    \item \textbf{incremental collectors} that do not stop the mutator
      to completely collect the heap: instead they partially collect
      what they can in a short cycle, making sure that, in the long
      run no dead object leaks (this is good for soft real\hyp{}time
      and interactive mutators, like games);

    \item \textbf{concurrent collectors} that do not stop the mutator
      at all, and even can handle multiple mutators sharing the same
      heap (think multicore architectures);

    \item \textbf{distributed collectors} that work when there are
      heaps managed on distinct physical computers, each running one
      or many mutators.

  \end{itemize}

\end{frame}
